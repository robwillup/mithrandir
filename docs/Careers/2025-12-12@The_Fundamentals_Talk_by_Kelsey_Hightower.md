# The Fundamentals by Kelsey Hightower

In the Q&A section, somebody asked this question:

Would it be right to say "less is more. Understand the actual need, keep it simple where possible."

Kelsey answered:

> Yeah, I think so 100%. And again, I want to be clear about how hard this is.
> When I was working at CoreOS [doing the containerization], I remember I was writing Golang and we built this thing
> 'The Container Network Interface' ... we wrote everything in Go, we have this company philosophy 'everything will
> be written in Go unless you're working on the operating system.'
> And I'm writing this network interface in Goland and I remember, during runtime, if you are using something like
> Golang to make a system call, and if the kernel context switches your system call can end up on a different thread
> and bad things happen when that happens. And so I'm like "hey, there's this bug" and the guy next to me named
> Eugene, he's a C and C++ programmer, and he's like "I think Go has a bug.", I said "you mean Go the programming
> language, the runtime has a bug?", I was like "dude, just say you don't know Go and you're trying to learn it so
> don't try to blame it on the runtime". And lo and behold, right in front of me he dumps the assembly generated by
> the Go compiler and he points out the bug, he's like "here, you can't do that. That's not how that's supposed to
> happen when you make system calls". He goes upstream to the Go repository, I'm watching like "Iii don't know,
> Rob Pike and guys are pretty smart", and he flags the bug and turns out this was a bug that had been plaguing
> docker for a very long time and other application written in Go he knew a layer below me, the building blocks.
> So I think this just reinforces this thing that you have to understand the fundamentals, and if you think you do
> look one layer below, and then maybe another set of fundamentals, and I know what you're thinking, "why do I need
> to learn all this if the LLM will learn everything." I promise you, if you can't tell what good looks like, you
> will not be able to tell the difference in what response you're getting. So I think there's some value in using
> tools like that as a shortcut, as an assistant, but if you can't tell what's good or right, how would you know
> whether we should be committing that to production or not? So I still think there's value in understanding these
> things.
>
